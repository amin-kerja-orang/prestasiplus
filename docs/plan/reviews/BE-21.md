## Security review (Pass)

Fix in the contract now every finding marked "contract now" with severity High or Medium. Items marked "implementation" go to the full card later.

- MEDIUM, belongs in the CONTRACT now: Credential response is not marked non-cacheable. POST /admin-sekolah/pelajar 201 returns credential.password in the body, but the path declares no Cache-Control: no-store (or Pragma) header on that response. Only the Amaran CSV declares no-store. A proxy or browser cache could keep a minor's plaintext password. Add the header to the 201 response and a CI test that asserts it.
- MEDIUM, CONTRACT now plus IMPLEMENTATION: The default password is a shared, configured, predictable secret. Per the schema docs, an empty or absent `password` means 'the configured default password', and it is echoed back in the 201 body. Anyone who learns the default (a printed hand-out, a screenshot, the response itself) can log in as every pupil still on it, and most of them are minors. BE-NFR-06 already says accounts on the shared default hash must be flagged must_reset_password, but the contract has no field or error for it. Recommend the server generates a random one-time initial password per account and returns it in the same credential.password field, so the wire shape does not change. If the shared default stays, the server must set must_reset_password and the contract needs a flag, for example `credential.mustChangePassword: true`, plus the login/session behaviour for it. The decision goes in the contract now; the generator and the flag go in the implementation card.
- MEDIUM, CONTRACT now: The 201 is not safely retryable. If the response is lost, a retry returns 422 'The email has already been taken.', the account exists and the one-time password is gone for good (reset-password is the only way out). Document the reset-password recovery path in the 201 description and say that credential.password must never be re-served. Optionally accept an Idempotency-Key header, in line with BE-NFR-18. The implementation must not store the plaintext to support a retry.
- MEDIUM, CONTRACT now: No 429 on any of the 24 routes. The `RATE_LIMITED` error with `retryAfter` and the `Retry-After` header (BE-NFR-04) is never declared in paths.ts. The riskiest routes need it: POST /pelajar (bulk account minting, e-mail enumeration through the 422 'has already been taken'), POST /guru, both reset-password routes, and both export.csv routes (a bulk dump of minors' names and e-mails). Declare 429 on all writes and on the two CSV exports. The numeric limits go in the implementation card and the runbook, because BE-NFR-04 notes there is no source for the non-login limits (OQ-9).
- MEDIUM, CONTRACT now: Cross-school e-mail enumeration by a school admin. Create and update return 422 'The email has already been taken.' when the address belongs to any user in any school (the rule says 'unique among other users', not 'among the school'). A school admin can therefore probe whether any e-mail address, including a minor's address in another school, is registered. This is a normal trade-off for unique e-mails, but it should be a recorded decision. Recommend documenting it, keeping the exact Laravel text only if the product accepts it, and rate limiting (see the 429 finding). Impossible to hide without dropping uniqueness, so the contract must state it plainly.
- MEDIUM, CONTRACT now: Contradiction between the card and the contract on the `admin` role. Card AC1 says 'restricted to school_admin (and admin)' and AC8 gives admin Amaran access to any school. The M27 routes (FORBIDDEN_SA and SCHOOL_ONLY) refuse every role except school_admin, so admin gets 403, and admin also has no school to scope to. Pick one: if admin is excluded (safer, and consistent with 'a missing school never means all schools'), fix the card; if admin is included, the contract needs an explicit school parameter, which breaks the 'no schoolId' rule. Recommend excluding admin from /admin-sekolah/* and amending the card.
- MEDIUM, CONTRACT now: Self-lockout and privilege rules are in the card but not on the wire. AC3 says toggle-active 'cannot disable the caller's own account', but the toggle route lists only 403/404, with no documented refusal for a self-toggle. The route is also restricted to teachers, so a school admin cannot be a target today, and the rule only matters if the managed roles ever widen. Add one sentence to the contract stating which error a self-target returns. An unspecified error will be implemented differently by backend and frontend.
- LOW, CONTRACT now: Inconsistent password policy. Create pupil requires 8 to 255 characters; update pupil, create teacher and both reset-password routes accept 6. A school admin can set a 6-character password on a minor's account. Align on 8 (the form-options already advertise passwordMinLength 8), or document the difference as a deliberate mock-fidelity choice. Note the frontend mock may show 6. Also set `maxLength` 255 on all password fields; password6 currently has no maximum, which allows very large inputs to the hasher (DoS). Cap at 255 or 1024.
- LOW, CONTRACT now: Minors' personal data in responses is larger than the CSV. List rows and detail return `phone` and `email` for pupils, while the pupil CSV explicitly omits phone and the detail states 'No IC number'. The IC position is good: no IC field exists in any request or response, which meets BE-NFR-10 and BE-NFR-11. Still, the guardian or pupil phone is not needed in the pupil list; consider dropping `phone` from SchoolAdminPupilRow and keeping it only in the detail. Also note the Amaran school risk page and CSV list pupil names with risk scores and class names, which is the most sensitive derived data about minors. Contract states 'IC, e-mail, phone never present', which is correct, but add a PDPA note on the CSV (Cache-Control: no-store is present on the Amaran CSV; the user CSVs lack a Cache-Control declaration, add it).
- LOW, IMPLEMENTATION card: Logging, audit and hash handling the wire cannot enforce. credential.password and newPassword must never reach logs, error bodies, request-body logging or APM (BE-NFR-11); `writeOnly` is only a schema hint. Required: redact `password`, `newPassword`, `credential` in the request logger and in the 422 `fields` echo. Audit events for pupil create, teacher create, reset-password, update with newPassword and both CSV exports (BE-NFR-08 names create, toggle and password reset but not export, so add export). Argon2id for new hashes (BE-NFR-06). Revoke all sessions of the target on reset (already stated).
- LOW, IMPLEMENTATION card: Scope enforcement tests. The contract is well shaped (other-school, other-role and unknown id all return the same 404 'Not Found.'; strict body, extra keys ignored). BE-NFR-05 asks for a strict schema that rejects unknown fields with 422, but this contract says other keys are 'ignored, never an error' for role, school, status, grade and icNumber on create and update. That conflicts with BE-NFR-05 (mass assignment test). Decide: the mock-fidelity 'ignore' is acceptable, but the card must explicitly note the waiver, and the implementation must prove role, schoolId, isActive and icNumber are never bound (test that a body with role=admin creates a student). Also test classId from another school returns 422 and never enrols. Also the inactive-account 403 on GET detail reveals that an in-school account exists and is inactive; harmless within the same school.
- LOW, CONTRACT now: Amaran routes expose scope parameters. /amaran/summary takes scope, schoolId, district and state, and /amaran/schools/{id} and /amaran/export/school/{id} take a school id. The contract says teacher and school_admin outside their reach get 403, but BE-NFR-05 says an out-of-scope id returns 404, never 403. The 404 for an unknown school versus 403 for another school's id lets a caller enumerate valid school ids. Recommend 404 for both on the school-scoped routes, or record the mock-fidelity exception next to BE-NFR-05 (the only approved exception is the Bijak attempt). The CSV route also states 404 before the access check, which is the leaky order; reverse it.

Recommendations:
- Before merge, amend the contract for the cheap wire-level items: add Cache-Control: no-store on the 201 credential response and on both user CSVs; declare 429 RATE_LIMITED (with retryAfter and Retry-After) on every write route, both reset-password routes and both CSV exports; document the retry and recovery rule for the lost one-time password.
- Decide the default-password policy now. Preferred: server-generated random initial password per account, returned in the same credential.password field, with must_reset_password set (add a flag to the credential or the session). If the shared default stays, record it as a risk acceptance and add the must-change flag.
- Reconcile the card with the contract: admin role handling (card AC1 and AC8 versus FORBIDDEN_SA), the self-toggle refusal, the 6 versus 8 character password minimum with an upper bound of 255, and 404 versus 403 for out-of-scope ids on the Amaran routes, so BE-NFR-05 holds or the exception is written down.
- Reduce minors' data: drop `phone` from the pupil list row (keep it in the detail), keep IC out of every response (already true), and keep the CSV column list unchanged. Add a one-line PDPA note on the exports and on the Amaran pupil lists.
- Put in the implementation card (not the contract): log and audit redaction for password, newPassword and credential; audit events for pupil create, reset-password and both exports; argon2id; per-route rate limits recorded in the runbook; integration tests for mass-assignment (role, schoolId, icNumber ignored), cross-school id returning 404, classId of another school returning 422, a log-capture test with no password in logs, and session revocation after reset.
- Record the e-mail enumeration (422 'The email has already been taken.' across schools) as a known and accepted trade-off, mitigated by the rate limit and the audit trail.
