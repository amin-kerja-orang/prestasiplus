## Security review (Fail)

Fix in the contract now every finding marked "contract now" with severity High or Medium. Items marked "implementation" go to the full card later.

- HIGH, contract now: The public invite preview (GET /parent-invites/{token}) returns the child's full name, initials and school name to anyone who holds the token, with no session. It is a minimal-disclosure design only if the token stays secret. Nothing in the contract adds a rate limit, a 429 response or a 'Cache-Control: no-store' note for this route or the accept route. The token is 64-hex (256 bits), so brute force is not realistic. The real risk is leakage of an unauthenticated link that names a minor. The routes with a path-carried secret are the ones where 429 and no-store matter most. Fix now: add 429 RATE_LIMITED (with retryAfter and the Retry-After header, as BE-NFR-04 does) to both token routes; list the unknown, used, expired and inactive-student cases as one indistinguishable 404 (already stated); state that the preview shows the first name or initials only, or confirm that full name is needed for the parent to recognise the child. Implementation card: per-IP throttle on the token routes, Referrer-Policy: no-referrer on the page that shows the link, and no logging of the raw path (log the route pattern only, per BE-NFR-27).
- HIGH, contract now (internal contradiction): The card says tokens are 'random, hashed and single-use'. The schema says the opposite in three places. (a) GET /me/parent-invite returns the clear token on every call, but a hashed-only store cannot return it again. (b) Accept is 'idempotent: an existing pair answers created:false', but a used token is a 404, so a replay cannot succeed. (c) The text 'shown in clear to the student; stored hashed' conflicts with (a). Either the token is reversible (encrypted at rest) and multi-use until expiry or regenerate, or it is shown once at generate time and GET returns only metadata (createdAt, expiresAt, linked parents). Recommendation: pick the second. Show the clear token only in the generate response, and give the first GET a path that mints a token. Say in the contract whether accept consumes the token. Several parents (mother and father) may need to use one link, so single-use may be wrong for the product. This needs a product decision, and the contract must say which. Expiry length is not defined anywhere (the card says only 'expiring'). Fix: put a maximum lifetime (for example 7 days) in the contract text.
- HIGH, contract now plus implementation: PDPA for minors. A parent-child link is created with no verification step beyond holding a link. There is no consent record, no guardian verification, and no way for the student, school or a parent to revoke or list-then-delete a link. There is no 'unlink' endpoint, and the linked parent's email is returned to the minor in ParentInviteLinkedParent. The URS itself says (BE-NFR-14, OQ-3) that data-subject rights and parent consent have no rule yet. Any adult who obtains the link, such as a forwarded message or a shared screenshot, becomes a linked parent with whatever access L45 grants. Recommendation: (contract) add an unlink operation, record consent metadata (acceptedAt, relationship, parent id) and define what a link unlocks; mask or drop the parent email for the student view (show name and relationship only); (implementation card) audit link and unlink events (BE-NFR-08 only lists 'subscription changes', add parent link and unlink), and raise the consent rule as a blocking open question before the accept endpoint ships.
- MEDIUM, contract now: No 429 appears on any of the new operations. BE-NFR-04 limits login, registration, password reset, upload and ticket creation. The new operations that need a limit are: POST /admin/students/import (a bulk create of student accounts with DELIMa passwords), POST /admin/comp-students, the two token routes above, and POST /me/parent-invite/generate (token churn). Add 429 to those responses now. Add the numeric limits to the implementation card, because OQ-9 says the registration, upload and ticket limits have no source.
- MEDIUM, contract now: The student import takes DELIMa passwords in clear in the request body (CSV rows are name, email, password, ic) and has no size or row limit ('the mock sets no file-size or row-count limit'). Risks: a huge body or a CSV bomb, a plaintext credential in transit and in memory, and the mock may have logged the body. Recommendation: (contract) set a maximum row count and file size (for example 1,000 rows, 1 MB, 413 or 422), and state that the response never echoes passwords or rows with passwords (the error list holds only line and message, which is good); (implementation card) hash the passwords on arrival, never log the body (BE-NFR-27), reject formula-leading cells in any re-export (BE-NFR-38), and run the import in one transaction (BE-NFR-17) so a quota check cannot be raced by two concurrent imports (the quota check and the insert need a lock).
- MEDIUM, contract now: The complimentary-student username is the last 6 digits of the IC plus '@prestasiplus.my'. It is also the login e-mail. The last 6 digits of a Malaysian IC are the place-of-birth code, a serial and the gender digit, so this identifier is derived from the IC and predictable, which makes username enumeration and password guessing cheap (the default password rule is not stated in the contract). It also appears in list and detail responses next to the masked IC, so the 'IC never leaves the API' claim is partly defeated (BE-NFR-10 is about storage and logs, but BE-NFR-11 minimisation applies). Recommendation: either generate a random username or add a collision-safe random suffix, and say the initial password is generated and forced through reset (BE-NFR-06 must_reset_password). If the format must match the live site (fidelity rule D9 allows a fix for a security defect), record it as a deviation. Also the bulk-action ids array has no maximum length; add one.
- MEDIUM, contract now: Free-text and payment fields have no length limits and no sensitivity rule. optionalText has no .max(). Affected: paymentReference, paymentNotes, notes, reason, the quota note, and the newline-joined history 'notes' returned in SubscriptionDetail. Staff can paste bank details, card digits or personal names there, and they are echoed back and appended to history. Recommendation: (contract) add .max() to every free-text field (for example 255 and 1,000); state that paymentReference is a reference and that no card or bank data is stored; (implementation) keep the history lines out of logs and audit content (BE-NFR-11), and write the actor and role into the audit trail, not into the visible notes.
- MEDIUM, contract now: The invoice and the subscription student list return minors' personal data in bulk. GET /admin/school-subscriptions/{id}/renewal-invoice embeds every student (no, name, idDelima, classLevel) in one unpaginated array, and idDelima is a school e-mail account of a minor. The list endpoint /admin/school-subscriptions is declared unpaginated too, against BE-NFR-16 (every list is paginated, pageSize at most 100), with no stated exception. Recommendation: (contract) keep the exception only if it is documented in the BE-NFR-16 deviation list; make the invoice return counts and totals, and move the student roster to the paginated /students endpoint (already present); mask idDelima (for example first characters and domain) or drop it from the invoice; mark all these responses Cache-Control: no-store (BE-NFR-40 for personal data). Implementation card: confirm the PDF or print output is generated client-side so the roster is not stored.
- MEDIUM, contract now: Scope is not stated for the school-side callers. Every route in subscriptions/paths.ts is described as 'admin only', and the forbidden response is a plain 403. BE-NFR-05 says scope comes only from the account and an out-of-scope id returns 404, never 403. The contract has schoolId in request bodies (create subscription, import) and id in the path (quota, students, comp-students/{id}). If the role is 'admin' (central admin) the schoolId field is legitimate. If a school admin can call POST /admin/students/import, schoolId must come from the account, not the body. The contract does not say which role may call what, and the 'assign package to a school admin' endpoints carry no scope rule beyond 'not a school admin'. Recommendation: (contract) name the permitted roles per operation in the access matrix, and say that the import and quota routes are central-admin only or that a school admin's schoolId is rejected if it differs from its own; (implementation) a cross-school test for each id route.
- LOW, implementation card: Enumeration. Route 404 vs 422 behaviour differs by existence: /admin/users/{id}/packages answers 404 for an unknown user but 422 for a user who is not a school admin, so an admin-level caller can tell user types apart. This is minor because only admins reach it. The same holds for comp-students/{id} (404 unless complimentary), which is the correct hiding behaviour. Subscription ids and the invoice ref (INV-{subscription id}-{date}) are predictable but admin-only. Add a note that ids are opaque and no sequential id is exposed, per BE-NFR-25.
- LOW, contract now: Validation messages are English Laravel templates ('The selected school id is invalid.') and can disclose that a school exists or is active ('Must be an ACTIVE school'). Admin-only, so acceptable, but the contract already flags the mix of BM and English copy. Keep it, and list it in the deviations table.
- LOW, contract now: Query parameters are unbounded strings and are described as 'never rejected' (perPage, page, status, formLevel, search). This is safe functionally, but search has no maximum length, so add .max(100) to avoid expensive LIKE scans. SQL injection is covered by BE-NFR-07 in the implementation card.

Recommendations:
- Fix the parent-invite token model in the contract before merge: decide stored form and use. Show the clear token only at generate time, let GET return metadata only, state whether accept consumes the token, and add a fixed maximum lifetime.
- Add 429 RATE_LIMITED (retryAfter body field and the Retry-After header) to the two public token routes, to /me/parent-invite/generate, to /admin/students/import and to /admin/comp-students. Put the numeric limits in the implementation card.
- Add an unlink operation and a consent and verification rule for parent links. Mask the parent's e-mail in the student's view. Raise parent consent (OQ-3) as a blocking open question for BE-25 accept. Extend the audit list in BE-NFR-08 to parent link, unlink and invite regenerate.
- Reduce the preview data on the public route (initials or first name and school), and mark every token-carrying or personal-data response Cache-Control: no-store.
- Add limits: maximum rows and bytes for the import, maximum length for every free-text field and for search, maximum length of the bulk ids array. State that passwords are hashed on arrival and never logged, and that the import runs in one transaction with a lock for the quota check.
- Re-think the complimentary username (IC-derived, predictable): use a random suffix, or record it as a deliberate deviation with a forced password reset on first login.
- Stop embedding the full student roster with idDelima in the renewal invoice. Return counts, and point to the paginated students endpoint. Document the unpaginated subscription list as a BE-NFR-16 exception or paginate it.
- Name the allowed role per operation in the access matrix (central admin only vs school admin), reject any scope field a school-side caller must not set (BE-NFR-05), and add a cross-school test for every id route in the implementation card.
