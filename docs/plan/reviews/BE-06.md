## Security review (Fail)

Fix in the contract now every finding marked "contract now" with severity High or Medium. Items marked "implementation" go to the full card later.

- HIGH, contract now. POST /auth/password/reset-ic (paths.ts) documents only 200 and 422, no 429. A correct email+IC returns a usable reset token in the body, and /password/reset then logs the attacker in (Session cookie set). A Malaysian IC has low effective entropy (6-digit birth date, ~2-digit place code, 3-digit serial plus a gender-parity digit); for a student whose birth year is roughly known and whose email is guessable, the space is on the order of 10^7. With no attempt limit this is account takeover of minors' accounts by online guessing. The 422 mismatch text is uniform, so it is also a guess oracle. Mock has no throttle either (resetByIc in mock/handlers/auth.ts), and the card AC6 limits only registration. Concern: contract (missing 429) plus implementation (the limiter).
- HIGH, contract now (the secret in the response is the design choice). reset-ic returns the reset token and the email in the 200 body, so knowledge of an IC alone equals full account control (token -> reset -> auto-login). There is no mailbox possession check, unlike /password/email. At minimum the contract must state: failed-attempt limit per (email) AND per client IP, lockout/backoff with Retry-After, the token entropy (>= 128-bit random, only a hash stored; the mock uses reset.id), Cache-Control: no-store on the response, and that a successful reset-ic is audited and sends the user a notification (NotificationsService.push) so a takeover is visible. Recommend the contract also note that the token returned here is bound to the email and can only be redeemed via /password/reset. Whether reset-ic should exist at all for minors (vs teacher/admin-assisted reset) is a product call for the lead (see OQ-3 below).
- MEDIUM, contract now. Throttle semantics are inconsistent. /password/email documents a 60 s per-email throttle that applies to unknown emails too, but reset-ic documents that issuing a token starts that throttle only on a match. This makes /password/email a side channel: after a reset-ic call, a 429 on /password/email for that address reveals the IC guess was right (and the throttle state for unknown emails has to be stored, an unbounded-memory/DoS vector). Recommend: key the per-email throttle on a hash of the normalised email for every request regardless of existence, start it on every reset-ic attempt (not only matches), and add a per-IP limit. A per-email-only limit also lets an attacker lock a victim out of resetting (targeted DoS), so use (email, IP) plus a global per-IP ceiling. Contract: add 429 RATE_LIMITED + retryAfter + Retry-After header to reset-ic and /password/reset. Implementation card: the actual counters.
- MEDIUM, contract now. The token-guessing surface of POST /auth/password/reset has no 429 and no stated token format. Even with a high-entropy token, the contract should state it is >= 128-bit random, compared in constant time against the stored hash, that issuing a new token invalidates all earlier unused tokens for that user (one active token), that a successful reset consumes every outstanding token of the user, and that failed redemptions are rate limited per IP. Currently only 'single use, 60 min, hashed' is written. Concern: contract text plus implementation.
- MEDIUM, implementation card (note in contract). Timing and enumeration side channels. Status and body of unknown-email and wrong-IC are identical (good), but the implementation must do the same work in both paths (dummy hash compare for unknown email or a user without a stored IC, e.g. teachers and parents who have no IC), otherwise latency leaks existence. The stored IC hash must not be a plain fast unsalted hash: a leaked DB would allow offline brute force of the small IC space; use an HMAC with a server-side pepper or argon2id (BE-NFR-10). Add an IT: response time class equal for the two paths, and an assertion that a user without an IC can never match.
- MEDIUM, contract now. The change of an unknown email on POST /auth/password/reset from 'We can't find a user with that email address.' (MSG_USER_NOT_FOUND) to 'This password reset token is invalid.' is correct and should be kept: it closes enumeration, and token-invalid on fields.email is the same status (422) as before. But it is not in card AC3 (the card lists only the e-mail request and reset-ic) and docs/plan/v2-backend-deviations.md is not touched in this branch (diff stat shows only backend-tracker.md). Action: log it as a deviation and ask the lead to confirm in Open question 1. Also the 403 ACCOUNT_INACTIVE on /password/reset is reachable only with a valid token, so it is not an oracle; but reset-ic should not issue a token for an inactive account (it currently would, then fail at redemption), to avoid issuing credentials to disabled accounts. That check belongs in the implementation card with a contract note.
- MEDIUM, contract now. Secrets and personal data in transit and logs. (1) The reset link in the mock is /password/reset/<token>?email=<email>: token and email in a URL end up in access logs, browser history and Referer. With MailPort that only logs the link in B1, the token and the email would be written to application logs, which conflicts with BE-NFR-11 (no e-mail, no secrets in logs). Recommend: the contract states the link carries the token in the URL fragment or a path the front end immediately exchanges, Referrer-Policy: no-referrer on the reset pages, and the dev MailPort logs only a masked email and a token id, never the token. (2) reset-ic echoes the email in the 200 body; the client already has it, so drop the field from AccountResetToken (data minimisation, BE-NFR-11). (3) the request body of reset-ic carries a full IC number; the contract must say request bodies for these routes are redacted from logs and error bodies (BE-NFR-10).
- LOW, contract now. Registration remains an enumeration oracle by design (422 'emailTaken' on fields.email). That follows the mock and the UX, so accept it, but it must be covered by the new 429 on /auth/register (present) plus a per-IP limit; document it as an accepted residual risk. The 429 for register states 'the mock has no registration throttle', so the mock tests cannot verify it; the implementation card needs an IT.
- LOW, implementation card. Reset flow hygiene: confirm that /password/reset (a) invalidates the user's other sessions and remember tokens, (b) rehashes with argon2id, (c) clears must_reset_password, (d) writes an audit event without the token, and (e) notifies the user. The contract mentions (a) only. A reset that logs the user in sets a non-remembered cookie, which is fine. Also add the Retry-After header explicitly to the 429 on /auth/password/email (the description says it, but only the body field retryAfter is declared in the response).
- MEDIUM, lead decision (PDPA / minors). Most users are minors and the IC number is a sensitive national identifier. OQ-3 in the URS states no requirement covers PDPA data-subject rights, parental consent or retention, and the reset-ic flow lets any classmate who knows a child's IC and email take the account. The contract cannot solve this alone: the lead should raise with the user whether IC-based self-service reset is acceptable for under-18 students, or should instead be teacher/parent-assisted with the token delivered out of band. Until decided, the limits in the High findings are the minimum. Also note the registration body collects an IC number (students) and referralCode; both are write-only in the contract, which is correct (IC never returned, only masked value, BE-NFR-10).

Recommendations:
- Before merging the contract: add 429 RATE_LIMITED (retryAfter and Retry-After header) to /auth/password/reset-ic and /auth/password/reset, and state per-(email, IP) plus per-IP limits, with the failed-attempt budget (reuse the BE-03 login throttle: 5 failures per 60 s, then backoff). Define the limits in the contract text so BE-31 conformance can test them.
- Specify the token in the contract: >= 128-bit random, only a hash stored, 60 min, single use, a new issuance revokes earlier tokens, a successful reset consumes all tokens of the user, constant-time compare. Add Cache-Control: no-store to the token-bearing responses.
- Make the throttle uniform: apply the per-email 60 s throttle to every /password/email and every reset-ic attempt, known email or not, so 429 is never a match oracle; document that reset-ic matches do not behave differently from misses.
- Remove email from AccountResetToken (the client already holds it). Keep icNumber write-only, mask it in logs, and keep the IC hash as HMAC-with-pepper or argon2id.
- Do not log the reset link, token or email in the dev MailPort; log a masked email and a token id only (BE-NFR-11). Put the token in the URL fragment or exchange it on load, and set Referrer-Policy: no-referrer.
- Keep the unknown-email -> 'This password reset token is invalid.' change, but record it in docs/plan/v2-backend-deviations.md and in the card's Open question 1, since it goes beyond card AC3.
- Implementation card (not contract): equal-work dummy hash for unknown email or users without IC, refuse to issue a token for inactive accounts, audit event plus NotificationsService.push on reset and on reset-ic, invalidate other sessions and remember tokens, ITs for lockout, token reuse and expiry, and a log-capture test proving no token, email or IC appears in logs.
- Ask the lead to put the minors question to the user (is IC-only self-service reset acceptable for students, and OQ-3 PDPA rights); security-engineer to re-review the implementation PR of BE-06 since the card marks it 'required'.
