# LEAD review: BE-06 contract (Group B), round 2

Verdict: **Request changes**. Date: 2026-10-19. Fix on `be/BE-06-contract`, rebase on `origin/feature/v2-backend`, then set the tracker row to `review`. Apply TRACKER decisions D55, D57 and D58 (see the AGENT-SYNC Lead notices).

## Code review: Majors (must fix)

- D57(a) is not applied. Every write route and every unauthenticated lookup must document 429 RATE_LIMITED with retryAfter and Retry-After. Only /auth/register, /auth/password/email and /auth/password/reset-ic have a 429. Missing on: POST /auth/password/reset (the token-guessing surface, also a LEAD review item marked 'contract now'), PUT /me, PUT /me/password (current-password brute force), POST /me/picture, PUT /me/settings, GET /public/stats, and all five notification write routes.
- D57(b) is not applied. No response that carries a credential or token documents Cache-Control: no-store. The affected responses are POST /auth/register 201, POST /auth/password/reset 200 and POST /auth/password/reset-ic 200. A grep of the account and notifications folders for 'no-store' and 'Cache-Control' finds nothing.
- LEAD review item not fixed: AccountResetTokenSchema still returns { token, email }. The review asked to drop email from the reset-ic 200 body, because the client already holds it.
- LEAD review items not fixed: the reset token spec is missing. Nothing states >= 128-bit random, hash-only storage, constant-time compare, one active token per user (a new issuance revokes earlier tokens), or that a successful reset consumes all of the user's tokens. Also missing are a note that reset-ic request bodies (IC) are redacted from logs, and that the dev MailPort logs only a masked e-mail and a token id, never the reset link.
- The throttle semantics inconsistency is still there. reset-ic says 'Issuing a token also starts the 60 second throttle of /auth/password/email', so a 429 on /password/email after a reset-ic call reveals that the IC guess was correct. The review asked for the throttle to start on every reset-ic attempt, match or miss, keyed on the normalised e-mail. The D55a attempt limit is documented, but this side channel is not closed.
- The deviations are not logged in docs/architecture/v2-backend-deviations.md (the diff does not touch that file). The deviations to log are: unknown e-mail on password/email returns 200; unknown e-mail on password/reset returns the token-invalid message (D55b); register and reset return the contract Session instead of {token, expiresAt, user}; AccountUserMe adds username and roles; bulk ids are Id strings. The card requires a dated row when deviating.

Minors:
- All 18 mock routes are covered with the same method and path, and there are no invented endpoints. Coverage: auth register, password/email, password/reset, password/reset-ic; me GET and PUT; me/password; me/picture; me/settings GET and PUT; public/stats; seven notification routes. The mock's /auth/login and /auth/logout belong to BE-03, and gamification-summary belongs to BE-11, so none of these are expected here.
- The D55a attempt limit (5 per 15 minutes, per account and per IP, 429 with the BM message) and the D55b invalid-token message for an unknown e-mail on reset are applied in paths.ts, and the tests use the shared ErrorBodySchema, envelopeOf and IdSchema helpers. I did not read the example payloads in the contract tests, so I have not confirmed they are taken from the mock.
- The tracker row is set to 'review' with PR #4. After the LEAD merges, the row should return to todo with 'contract merged', which is the LEAD's step. A typed retryAfter field in the 429 body is not declared; this is consistent with the other lanes.
- Optional: make the tests stronger by using payloads copied verbatim from the mock handlers, for example the 429 body with retryAfter.

## Security re-review (Fail)

- HIGH, contract now: AccountResetTokenSchema in account/schema.ts (about line 318) is still strictObject({ token, email }). The email field was NOT removed from the reset-ic 200 response, although the first review (and the brief for this re-review) required it. This leaves a wire-level data-minimisation (BE-NFR-11) gap, and the 'reset-ic returns a bearer token' design is unchanged. Recommendation: make the schema { token } only (the client already has the email) and regenerate openapi.json.
- HIGH, contract now: reset-ic returns a usable reset token to anyone who knows an e-mail and an IC number. D55a (5 attempts per 15 min, per account and per IP, 429 with retryAfter and Retry-After) is in the contract and the 429 response is declared. That is the minimum fix. It reduces but does not remove the minors-takeover risk: a classmate who knows the IC and e-mail still takes the account with no mailbox proof. No audit or user-notification requirement is written for a successful reset-ic. Recommendation: add contract text that a successful reset-ic is audited and sends the account owner a notification (NotificationsService.push). The residual risk is a lead/user decision (see the PDPA finding).
- MEDIUM, contract now: POST /auth/password/reset has NO 429 response (only 200, 403, 422). The token is the guessable surface, and the task asked for 429 on both reset-ic and reset. D57a requires 429 on every unauthenticated write. Recommendation: add 429 RATE_LIMITED (retryAfter and Retry-After header) per client IP and per email-hash, and state the failed-redemption budget (reuse the 5 per 15 min of D55a).
- MEDIUM, contract now: throttle uniformity is not achieved. The /password/email description says the 60 s throttle applies to known and unknown emails alike (good). The reset-ic description still says 'Issuing a token also starts the 60 second throttle of /auth/password/email for that e-mail', i.e. only on a match. A 429 on /password/email after a reset-ic call therefore reveals that the IC guess was right (match oracle). Recommendation: delete that sentence, or start the /password/email throttle on every reset-ic attempt, hit or miss, so a 429 never discloses a match.
- MEDIUM, contract now: the token spec is incomplete. The contract says only 'valid 60 minutes, single use, stored hashed'. It does not state: at least 128-bit random, constant-time compare, one active token per user (a new issuance revokes earlier ones), a successful reset consumes all of the user's tokens, or that a reset-ic token is bound to the e-mail. Recommendation: add these sentences to the reset, reset-ic and email route descriptions so BE-31 conformance can test them. Only the entropy, single-use and invalidation rules are contract-level. The constant-time compare itself is implementation.
- MEDIUM, contract now: no Cache-Control: no-store is declared on any token- or credential-bearing response (reset-ic 200 body token, reset 200 Session with csrf, register 201 Session). D57b requires it, and the paths.ts grep finds no 'no-store' anywhere. Recommendation: declare a response header Cache-Control: no-store on those three responses (and Retry-After on the 429s as an explicit response header, not just in the description and body).
- MEDIUM, lead decision (PDPA, minors): most users are minors and the IC number is a national identifier. The IC-only self-service reset (reset-ic) is still allowed for students. The contract cannot fix this alone. The URS OQ-3 (data-subject rights, parental consent, retention) is still unanswered. Recommendation: the lead should ask the user whether IC-based reset is acceptable for under-18 accounts or should be teacher-assisted, and record the answer as a decision. D57f gives parents unlink rights, but there is nothing equivalent here.
- MEDIUM, contract now (process): the deviations from the mock (unknown e-mail on password/email returns 200; unknown e-mail on password/reset returns the token-invalid message; register and reset return the contract Session; AccountUserMe adds username and roles; reset-ic gets a 429 that the mock lacks) are recorded in schema header comments and TRACKER D55, but NOT in docs/plan/v2-backend-deviations.md (no BE-06 or reset row). The card requires a dated row. The branch diff touches only the tracker, not the deviations doc. Recommendation: add the dated row(s).
- LOW, contract now: the register 429 only has a prose description (the mock has no throttle; per-IP limit not specified). Registration stays a deliberate enumeration oracle (422 emailTaken). Recommendation: state the per-IP limit and record the enumeration as an accepted residual risk.
- LOW, implementation card: the contract does not say that request bodies carrying icNumber or passwords are redacted from logs and error bodies (BE-NFR-10/11). It also does not say the reset link must not carry the token and email in a logged URL, or that the dev MailPort logs only a masked email and a token id. Recommendation: put these as short contract notes and as implementation ITs (log-capture test).
- LOW, implementation card: equal-work dummy hash for unknown email or users without an IC (timing); IC hash as HMAC with pepper or argon2id; refuse to issue a token for an inactive account; on reset, invalidate other sessions and remember tokens, rehash with argon2id, clear must_reset_password, write an audit event without the token, and notify the user. ITs: lockout counters per account and per IP, token reuse and expiry, response-time class equal for hit and miss.
- Verified as FIXED: reset-ic 429 declared with retryAfter, constants ACCOUNT_RESET_IC_MAX_ATTEMPTS=5 and WINDOW=15 min per account (e-mail, existing or not) and per IP, every attempt counted, BM copy added; unknown e-mail and wrong IC are indistinguishable (422 icMismatch on fields.email); unknown e-mail on reset gets the token-invalid text (D55b); /password/email answers 200 for known and unknown e-mail and its 60 s throttle applies to both; IC and password are never returned (GET /me excludes them); inactive accounts get 403 only after a valid token.

Recommendations:
- Before merge, fix in the contract: drop email from AccountResetToken; add 429 (body retryAfter plus Retry-After header) to /auth/password/reset; remove the 'issuing a token starts the 60 s throttle' sentence from reset-ic (or make the throttle start on every attempt); declare Cache-Control: no-store on the reset-ic, reset and register responses; add the token spec (at least 128-bit random, one active token, consumed on success, bound to e-mail); then run npm run contract:emit and update the contract tests.
- Add the dated deviation rows in docs/plan/v2-backend-deviations.md and state the per-IP limit for register; mark the register e-mail enumeration as an accepted residual risk.
- Put in the contract text that a successful reset-ic is audited and notifies the account owner.
- Move to the implementation card with ITs: equal-work dummy hash, HMAC-pepper or argon2id IC hash, no token, e-mail or IC in logs (masked e-mail and token id only), session and remember-token invalidation, inactive-account refusal, lockout counters per account and per IP.
- Ask the user (lead decision) whether IC-only self-service reset is acceptable for under-18 students, and answer URS OQ-3 on PDPA rights, parental consent and retention.
- Re-review after the fixes, and security-engineer to review the implementation PR as the card requires.
