## Code review

- **Major:** Guru POST /api/guru/questions does not reproduce the mock's BM messages or per-type rules (QuestionGuruCreateRequestSchema). Compared with m10 handlers/questions.ts parseCreate and common.ts MSG: (a) educationLevelId, subjectId and difficultyLevel have no message, so a missing value gives 'Invalid input: expected string, received undefined' or 'Invalid input'. The mock gives 'Sila pilih tahap pendidikan.', 'Sila pilih subjek.' and 'Sila pilih tahap kesukaran.'. (b) Missing questionText gives an English zod message, not 'Sila isi soalan.'. (c) The per-type rules are not enforced. An mcq with no options or key, a true_false with no tfAnswer ('Sila pilih betul atau salah.') and a short_answer or fill_blank with no answer all parse OK. The mock's answer-text error is keyed on field `correctAnswer`, with 'Sila masukkan jawapan betul.'. (d) Missing messages for per-option length over 500 ('Pilihan jawapan tidak boleh melebihi 500 aksara.'), correctAnswer text over 500 ('Jawapan betul tidak boleh melebihi 500 aksara.'), invalid chapter, topic and script type, and the image message under field `questionImage`. QUESTION_MESSAGES.guruTf, guruChapter, guruTopic and guruScript are declared but never used, so scriptType gives zod's 'Invalid option: ...'.
- **Major:** Guru PUT /api/guru/questions/:id (QuestionGuruUpdateRequestSchema) has the same gap. Missing questionText gives an English message. optionText min(1) gives 'Too small: expected string to have >=1 characters' and not 'Sila isi semua pilihan jawapan.'. correctOptionId has no 'Sila pilih jawapan betul.' message and gives 'Too big: expected number to be <=3'. The mock keys these errors on `options` and `correctOptionId`, but the contract's issue path is `options.0.optionText`. The mock also requires all four option ids to be unique, and an mcq edit requires correctOptionId whenever options is sent. Neither rule is expressed.
- **Major:** Admin and Guru field-key mismatch on per-element errors. The mock reports `fields.options` (one key), but the contract's issue path is `options.1`. In the probe, create with options ['a','','c','d'] gave path `options.1`. Whoever maps issues to `fields` will get a different key than the mock unless the contract fixes the path, for example with a superRefine on the array. Also, `correctAnswer: 5` gives the right message, but the key has to be unambiguous in the OpenAPI description.

That is acceptable for a service-level rule, but it should be stated as a service rule. QuestionCurriculumTag allows an empty spIds and a null tp.
