## How to read this

- AC4 (card BE-33): every item of the audit list writes a row with actor, role, scope, action, target and request id, never personal content. Mandatory list: role switch, mode enter/exit, user create/delete/toggle (BE-05), subscription changes (BE-25), question publish (BE-10), password reset (BE-06), Mod Pelajar (BE-03/BE-21). Everything else is a recommendation.
- Fields legend: A actor user id, R actor role, S scope level, Sch scope school id, T target type and id, Q request id, IP keyed IP hash (never the address). `AuditService.record` stores whatever the caller passes; it redacts secret-looking keys and IC numbers in `details` (`audit.service.ts:56-74`) and validates `targetId` as decimal or uuid.
- Status: CT = Covered+tested, CU = Covered-untested, GAP = Gap (no audit row, or the mandatory record is incomplete), NR = Not required (justified).
- "Mand." in the Owner column marks an item of the card's mandatory list.
- Personal content: no audited path puts a name, e-mail, IC, phone, password, token or free text into `details`; they carry ids, counts, field names, flags and enum values. Admin-authored catalogue text appears in a few rows (tier name, challenge title, draw title, intake paper type and subject): low risk, Perlu pengesahan that no pupil or teacher can type into those fields. The whole-table scan test in `audit-coverage.spec.ts` (last test) checks e-mail, dashed IC, session values and one password only.

## Systemic observations (verified in code)

1. Session rows have no target. `session.*`, `auth.login.succeeded` and `auth.logout` store the session id only in `detail.sessionRowId`; `target_type` and `target_id` are null (`auth.service.ts:189, 217, 323`). The card asks for a target on role switch and Mod Pelajar. The fix is two fields (patch P1; `targetId` accepts the session uuid).
2. Scope level is missing on several writers: logout, password change, profile, register, question.* rows, gamification admin, shop admin. Writers that use a shared `auditBase` (users, schools, subscriptions, content, school-admin) all fill it.
3. Question publish is the weak point. The only HTTP route that changes a question status is `POST /questions/bulk-action`; it calls `QuestionsService.setStatus` directly (`questions.service.ts:267, 282`) and never the BE-10 lifecycle, so no `question_status_events` row is written on the real publish path. `QuestionWorkflowService.transition` is called only from tests. The existing test proves the service path, not the route; the `it.fails` "BE-10" test documents the route gap.
4. Some audit calls are outside the business transaction: question.* (called after the service returns), file.* (swallowed on failure), password-reset request rows (swallowed on purpose). A failed audit write after a committed change leaves no row. Acceptable for the public reset flow; recommended to fix for question writes and files.
5. The `it.fails` blocks in `audit-coverage.spec.ts` correspond to: BE-03 session target (P1), BE-06 role and scope on reset (P2; the request row has no authenticated actor by design, so that part of the test should accept A=null), BE-10 bulk status events and scope (P3, P4). Remove each marker when its fix lands.
6. Personal data: no audited writer passes names, e-mails, IC, phones, tokens, voucher codes, payment references, ticket text or comment text. Draw rows list winning user ids and ticket ids (pseudonymous ids). Request ids are client-supplied safe tokens; Perlu pengesahan that the request-id middleware caps the length.
