## 0. How the tooling behaves (decides the design)

- Every loader upserts by legacy_source/legacy_id via etl_id_map into the EXISTING UAT DB. No stage needs a table reset. `rebuild-db.sh` (drop and refill) is NOT used; stages call `slot.sh` directly.
- **Question bank loaders (stages 2 to 4) are insert-if-missing.** An existing question/paper is never rewritten (so admin edits survive); V2 edits or status changes to rows already loaded are NOT refreshed (consistent with KP-14). Papers: `--recompute` stays OFF (KP-18 defers it to cleanup).
- **Core/activity loaders (stages 1 and 6) overwrite a migrated row when it differs from V2** (hash compare on big activity tables, column compare elsewhere). They cannot tell "V2 changed" from "V3 admin edited". V3-only rows (legacy_source NULL) are never touched.
- **Rows deleted in V2 since the last dump:** never deleted or demoted in V3 (not propagated, KP-14). `migrate:verify` lists them as `deleted_at_source` and fails if more than the ceiling (guards an incomplete dump).
- `slot.sh copy` replaces the whole `staging_cloud` + `archive_cloud` schemas; `public` is untouched. Staging is copied ONCE (stage 0) and kept until stage 6 ends.

## 1. Common stage protocol

1. Stop api (ETL and API never run together). 2. Restore point: `backup/backup.sh --tag pre-rebuild --no-files` (whole-DB `pg_dump -Fc`, sha256, `pg_restore --list`), then COPY it to `/var/backups/pretasiplus/clone-stages/stageN-*.dump` (backup.sh retention only keeps the newest few). Dumps hold raw staging data: wipe them at the end. 3. Load. 4. `ANALYZE;` as DB owner (`su_psql`) after every stage (stale-stats perf finding). 5. Checks, start api, UAT functional check. 6. PO go/no-go, only then next stage.
**Stage-only rollback = restore that stage's own pre-stage dump** (state after the previous stage, so earlier stages stay): first `echo 56febfae4 > /var/lib/pretasiplus-deploy/rebuild-prev.tag` (else the restore starts an old release), then `rebuild-db.sh --rebuild-db --restore-backup FILE` (guards G1-G4, typed confirmation, needs PP_ALLOW_DB_REBUILD, temporary). Not delete-by-etl-run: `migrate:rollback` deletes ALL rows of the source, and restoring single tables breaks FKs from V3-only rows. On failure we roll back the LATEST stage only and stop; stages are never undone out of order. Restore time scales with DB size (166 MB took 123 s in the 2 Nov drill): measure at stage 0.

## 4. Risks and what cannot be staged cleanly

- Stage 3 repoint and the later `--recompute` change what stage 4 placements point at: a stage-3 rollback after stage 4 is impossible, so only the latest stage is ever rolled back. Placement repair itself (KP-16, recompute) stays in cleanup.
- V2 status/text edits to already-loaded questions and papers are not refreshed (by KP-14); users deleted in V2 stay active in UAT. PO should confirm this reading of KP-5.
- Stage 1/6 split depends on the slot.sh whitelist change (gap 1); stage verify depends on manual entity filtering (gap 2).
- Raw personal data of minors: staging_cloud and every stage dump hold it; `PP_RAW_PURGE_BY` (6 Nov) is already overdue: PO sets a new date.
- Disk: 6 whole-DB dumps plus staging (guard needs 5 GB free): measure DB size first. Whether the API reads `archive_cloud` while it is replaced: keep api stopped during copy.
